# Repository skills

Use a repository skill only when its trigger matches the task. Read its `SKILL.md` entry section first; follow links to supporting files only when the selected workflow needs them. Keep new skill descriptions to one sentence stating the deliverable and the narrow trigger. Put long reference material, examples, and scripts in supporting files so the entry document remains a router.

Prefer the smallest applicable skill set. If repository rules and a skill overlap, keep the stricter concrete constraint once and remove duplicated prose. Skills should guide decisions and acceptance checks, not prescribe every shell command or force unrelated tests.
